MotherDuck Dives + Flights · cookbook recipe

Malleable Dives

A Dive whose layout, charts and words come from a spec a Flight writes. Every morning it writes a briefing; ask a question or investigate an insight and it writes a new page. Then you rearrange it, rate it, and the next analysis learns from what you did.

01Design the componentsmotherduck-dive-components skill

Dives can only import React, Recharts, d3 and lucide, so the components travel as source code, the shadcn way. dive-components/kit/*.tsx holds the components, and assemble.py copies the ones a Dive needs into its single index.tsx.

kpiStats, metric cards, compact stats or gauges
line · areaTrends; area adds headline value and legend toggles
bar · tableCategories against the previous period; rankings
driversWhich values of every dimension moved a number
heatmapA calendar of days, or a category against weeks
sankeyHow a count flows from one category to another
treemapPart-to-whole, grouped, click to zoom
timelineEvents in order, such as detected shifts
callouts · textInsights with an Investigate button; prose
date pickerA date or range for the viewer to choose
questionsWhat the page asks its viewers; answers become notes on the charts
form · fieldsshadcn-style Field, with label, description and error, inputs, selects and choice cards

components.json describes each component once: the data it takes, when to use it, which other components can show the same data, and a plan_rule that tells the Flight's planner when to pick it. Every component, built-in or custom, registers itself the same way:

registerComponent('funnel', {
  label: 'Funnel', icon: Filter, render: FunnelBlock,
  variants: ['bar', 'table'],              // what a viewer may switch it to
  accepts: (b) => b.series[0].format === 'count',
});
SwissPaperDuckNightmakeTheme({ base, accent, font, radius })

Blocks also carry the narrative around the chart. BlockInsight adds a "so what" line under a chart, and the About panel shows the definitions of what it measures and why it is on the page. Insights show a continuity chip, such as New, Ongoing since 12 Dec · 3 briefings or Resolved, and thumbs up and down for rating.

Four themes plus brand themes built from a base and a few tokens. The gallery, gallery/index.html, shows every component on sample data and opens in any browser; the same code runs as a gallery Dive.

02Describe the dataa recipe, written by an agent with the malleable-dive skill

It starts with an interview. Before writing anything, the agent asks the owner eight questions, skipping what the data, existing Dives and Guides already answer:

  1. Who reads the briefing, how often, and what do they decide?
  2. Which 3 to 5 numbers matter, how are they defined, and which are better when lower?
  3. What are the targets, and what size of change is worth reporting?
  4. Compare with what: last period, last year, or the target?
  5. Which breakdowns explain a change, and which to ignore?
  6. Which known patterns, events or data quirks matter?
  7. Who acts on which kind of insight?
  8. Which questions do you expect to ask?

The answers go to three places: a MotherDuck Guide under the topic briefings/<db>, which the Flight reads before every analysis; the recipe; and questions.json, the eval set. After the first briefing the agent asks once more: which insight would you act on, which is noise, and what is missing?

A recipe is one Python file that describes the data in words a model can use, and one JSON file for the brand. The template and the components stay the same.

03Create the Flightruns on MotherDuck, daily at 06:00 UTC and on demand

One Python program with five modes: briefing (the morning overview, from the fixed plan), ask (a question), investigate (an insight's question, with the page it came from), refresh, and feedback, which only records viewer events. Any run also records the events the Dive sends in its FEEDBACK config key. Only briefing and refresh rebuild the marts, so questions stay fast.

Every number in the narrative is checked against the data, the follow-up queries, the Guides and earlier insights. If fewer than 85% match, the narrator retries once with the missing numbers named, and the better draft wins. The memory Guide is written with MD_CREATE_GUIDE the first time and MD_UPDATE_GUIDE after that, so each version is kept.

A spec holds data and presentation, never SQL the Dive would run. That's why the Dive needs read access to one table only, and why a bad generation can't break the page.

04Create the Diveone .tsx file, pushed with the MotherDuck CLI

The Dive's only SQL reads dive_specs. It parses the spec and hands each block to its component through the registry, so it loads fast and never needs access to the source data.

Pages

Briefings, answers and investigations, newest first, with each investigation listed under the page it came from.

Data as of

A date picker on a briefing. Pick an earlier date and the Flight writes the briefing as it would have read that day.

Context for AI chat

The open page's question, headline and component titles go into useDiveState('context'), which MotherDuck AI chat reads with each message.

Under each title, a line says what the page drew on, for example Remembers 3 earlier briefings · 2 Guides · 3 follow-up queries · 40/40 numbers checked. Insights and pages have thumbs up and down. A Dive can't write to a database, so ratings go to the Flight straight away in a feedback run. Other signals, such as chart switches, hidden blocks and Investigate clicks, ride along with the next run the viewer starts.

When the data shows what moved but not why, the page asks. Under the insights, Questions for you holds up to two questions about a date or a segment, such as "What caused Other-channel visitors to jump in the week of 2 Nov?", with likely explanations to pick from. A viewer can also pin a note to any week or value with a chart's pin button. A note shows at once on every chart with that date or value: a marker on line charts and a line under the chart.

An investigation filters every block to the segment the insight is about, and adds a drivers table that ranks which values of every other dimension moved the number. In testing, a spike in “Other” traffic came down to a single referring site; the same page showed nearly all of it came from one browser on desktop, which points at automated traffic rather than growth.

Each component can switch to any other that can show its data: a KPI row to gauges, a line to a heatmap. Hide what you don't need, switch the theme, or reset. The arrangement is saved per page in useDiveState('layout'), travels with the link, and always wins over the generated layout. Generating a new page never moves an existing one.

The Dive also learns defaults. When viewers switch a block type to the same chart type 3 or more times, that chart type becomes the default for every block of that type. A viewer's own choice still wins.

The Dive's Memory page reads the same tables. It shows the insight timeline, what viewers ask, what they did, and each prompt version.

Improving prompts and models

The prompt version is a hash of every instruction and schema, so it changes whenever a prompt does. eval.py scores the planner on recipes/<name>/questions.json, and with --narrate it also scores how many numbers are grounded in the data. The Memory page compares prompt versions and models on speed, grounded share, eval score and ratings.

On NYC 311, the planner scored 1.00 on all 12 questions, and the narrate eval grounded every number on 3 questions. One prompt change, from version 0cb291cfec to 04751d1f87, kept those scores and cut the average time from 22.5 to 19.7 seconds.

One Flight, many triggersa single Flight per recipe, with five modes

Each recipe deploys one Flight. Every trigger runs the same main.py, and the MODE config key decides what that run does. One Flight means one owner token, one run grant for viewers, and one place that checks every input.

Config sent with a run overrides the Flight's config for that run only. The Flight checks every value a caller can pass: a known mode, id formats, a 600-character prompt, ISO dates and the shape of each event. MODEL picks the prompt() model. The Dive follows a run with useFlightRun and finds the new page by its REQUEST_ID. eval.py runs the same engine on your machine, outside the schedule.

One Flight for several Dives

Any number of Dives can read one output database today, for example the same briefing in a different theme or embedded elsewhere. They share every page, note and rating. Kinds of note: event, release, campaign, data issue, expected, not important, and other, for when it's unclear what happened. A question nobody answers stays on later briefings' pages instead of being asked again in new words. The Flight drops an event with an unknown dimension, a malformed date or an unknown kind. Remove on the Memory page sends an unannotate event, which marks the note inactive. In testing, two notes on NYC 311 changed the next cloud briefing's text to "Viewers noted Winter Storm Elliott on 2022-12-19 and fewer agency staff during the holiday week of 2022-12-26."

Three layers

Components

Developer-owned. The component kit, its catalog and its themes, copied into each Dive as source.

Content

Flight-owned. Which data, which components and what to say, written as a spec each time the schedule fires or someone asks or investigates.

Arrangement

Viewer-owned. Rows and slots, each component's variant, hidden components and the theme.

Memory

Shared. The log tables and the recipe's Guides, which the next analysis reads back.

# from generative-briefing-dive/
export MOTHERDUCK_TOKEN=...
python3 build.py recipes/nyc-311
cd recipes/nyc-311/flight
MODE=briefing REQUEST_ID=t1 uv run --with duckdb==1.5.6 python main.py
cd ../../..
uv run --with duckdb==1.5.6 python eval.py recipes/nyc-311 --out baseline.json
uv run --with duckdb==1.5.6 python deploy.py recipes/nyc-311
READMEThe interview questions, what to adjust for your own data, deploying and sharing. LEARNING.mdThe log tables, memory, Guides, viewer notes, the number check and evals in detail.

To adapt it, copy recipes/nyc-311 to recipes/<name> and replace domain.py, app.json and questions.json. The template and the components stay the same.
